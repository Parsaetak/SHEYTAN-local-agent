Go↔C++ boundary decision
------------------------
B) supervised native subprocess + IPC (shtn-engine-host, 4-byte
little-endian length-prefixed JSON over stdin/stdout, 1 MiB frame cap,
protocol/ABI handshake failing closed). Chosen over cgo/shared library
for: crash isolation (native crash cannot kill the app; bounded watchdog
restarts), preserved CGO_ENABLED=0 Windows cross-build, Android service
mapping, explicit versioned protocol, coarse-grained-only ops (the
boundary never carries tiny high-frequency calls). Documented in
internal/native/engine/doc.go and ARCHITECTURE.md §I.9.

Known limitations
-----------------
1. No native inference (by design in Phase 1) — see above.
2. The shtn-engine-host binary is not shipped or auto-downloaded; build it
   from native/engine/ (CMake or Make) into {DataDir}/bin/ (or configure
   nativeEnginePath) to use engineBackend: "native".
3. The C++ hardware probe detects CPU/RAM/architecture only; GPU and
   NPU/accelerator entries come from the Go sysinfo merge (real detected
   values) or stay empty until a C++ detector exists.
4. The Wails/GTK desktop build cannot compile in this Linux environment
   (no GTK4/WebKit dev libraries) — pre-existing v1.1.4Z limitation; the
   Windows CI job builds the desktop binary (CGO_ENABLED=0 cross-compile
   verified via go build; the desktop GUI itself is CI-built).
5. The native engine watchdog uses a STRICTER episode policy than
   llama.cpp (auto-restarts never reset the budget: 3 recoveries, then
   terminal failed). llama.cpp's own watchdog semantics are intentionally
   untouched.
6. engineBackend has no Settings UI control in Phase 1 (opt-in is via
   config.json or SHEYTAN_ENGINE_BACKEND) — deliberate: a toggle whose
   only visible effect today is a supervised process would be feature
   theater.
7. Cross-platform C++ paths (Windows cpuid/GLPI/psapi, macOS sysctl/mach)
   compile guarded but were executed only on Linux in this environment.
